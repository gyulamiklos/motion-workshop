# Motion breakdown → recipe

We learn the technique (timing, easing, choreography, layering), never the footage: no frames, logos, text, music or characters of the reference end up in our work.

**Workshop:** `$MOTION_WORKSHOP`, or the current repo when it has `tools/breakdown/` (`$WS`). Commands below run from `$WS`.

1. **Get the file.** A local file from the user, or a link the user asks you to fetch for private technique study: `yt-dlp --no-progress --js-runtimes node -f "bv*[height<=1080][ext=mp4]+ba[ext=m4a]/b[height<=1080]" --merge-output-format mp4 -o "research/<name>/source.%(ext)s" <url>` (`scripts/doctor.sh` says whether `yt-dlp` and `ffmpeg` are there). The file stays in `research/<name>/` (git-ignored) and never goes anywhere else.
2. **Measure:** `tools/breakdown/breakdown.sh research/<name>/source.mp4 research/<name>/bd` writes `meta.txt`, `cuts.txt` (scene change + one-frame motion spikes), `shots.txt` (number, start, end, length), `motion.csv`/`motion.svg` (per-frame motion energy: ramps show easing, flat stretches are holds) and `overview-P.jpg` (the whole video, at most 3 pages). Shot sheets come by themselves only for videos up to 30 s; otherwise ask for what you need: `--shots 5,6` (every 3rd frame), `--range 40.3-41.7` (every frame, 48 tiles max), `--crop W:H:X:Y` with `--range` (one region at full resolution).
3. **Rank the scenes, then pick the technique.** A long film or a music video holds dozens of moves. From the overview, list the candidates, one line each with the timestamp: what is striking and why it would be worth having. Rank by visual value (how much it would widen what our films can show: fog, crowds, true blur, physics, a new kind of 3D), never by how easy it is to measure; an easily measured text line is the usual wrong pick. Agree the pick with the user unless they named it; take one technique per pass. Each technique is a self-contained kit piece with its own card, used by some films and not others: do not copy the reference's scene, build the piece.
4. **Read it closely:** the shot sheets and range sheets of that move. For each move write: what moves, start and end frame, the curve (accelerating, decelerating, overshoot: read the positions frame to frame), what happens in parallel, the hold after it. Find at least two instances in the reference when it repeats; the difference between them shows what is a parameter. Sample colours from frames (ffmpeg crop to raw RGB), never guess them. Cheap tokens: read sheets, not single full-size frames.
5. **Check the kit first, then write the card.** Read `recipes/_principles.md`, `recipes/line3d/cards/` and `recipes/blender/cards/`; reuse a piece that exists, extend it or add one. A new piece gets a card in the kit's `cards/` folder (`recipes/blender/cards/<piece>.md` or `recipes/line3d/cards/`), a plain 2D HTML move gets `recipes/<name>/card.md`. The card is in the video-shotcraft shape: one sentence; use when; duration and energy; intent (why it works); motion core (the mechanics with measured numbers); a parameter table (value, how it feels when pushed up or down); known pitfalls; the reference (local path, never committed).
6. **Build it with the cheapest engine that reaches the look** (`recipes/blender/README.md`, "Which engine"): HTML + GSAP for 2D and text; the Three.js kit (`recipes/line3d/`) for quick wire 3D; Blender (`recipes/blender/kit.py`, run only through `scripts/blender.sh`) when the look lives on light, haze, a crowd, real motion blur or physics. A block is `recipes/<name>/<name>.html` (variables for copy and colours, GSAP timeline, brand-neutral defaults); a Blender scene is `recipes/<theme>/blender/<scene>.py` with a `<scene>.hud.json`, built into a block by `scripts/blender-block.sh`. Re-skin with a brand's `frame.md` when it goes into a film.
7. **Verify by eye and by measurement.** Look first: render at 60 fps (`--fps 60`), put it next to the reference at half speed (`ffmpeg ... hstack`), and show the user; their eye is the final measure (a Blender scene: `--pick` frames and a contact sheet before a full render). Then measure. Render the block with the reference's timing, at the reference's fps, with our own copy: `scripts/render-block.sh recipes/<name>/<name>.html research/<name>/ours.mp4 --fps 60 --duration 2 --variables '{...}'`. Measure the region where the move happens in both, starting at the same moment (`--from`), and compare: `python3 -I tools/breakdown/track.py measure <video> --roi W:H:X:Y --from S --to S --accent '#rrggbb' > x.csv`, then `track.py compare ref.csv ours.csv` (exit 0 = every event within 2 frames). Look at a reference frame and ours side by side too. At most 3 rounds; then report what still differs.
8. **Tell the user** what the technique is in one paragraph, where the card and block are, how close the measurement came, and one idea for where it fits in one of the brand's films.
